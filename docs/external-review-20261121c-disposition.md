### 2.2 事实错误

**① §0「形态：本地 Python 服务 + SQLite + Android 三页，**不联网**」**

判分链路要调模型 API：`llm_client.py` 读 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` 三件必需项，
`README` 的环境步骤就是 `copy .env.example .env # 填入 API key`。
准确说法是**分层**的：Android 端不联网；判分侧只有在 judge 双判开启时才出网，
纯确定性断言不需要网络（当前 12 个任务 0 条 llm 类断言，judge 默认关）。
写成「不联网」是**说过头**——这正是本指南 §3.4 自己要拦的毛病。

**② §5「Android 输入方式收缩到纯文字：外部建议如此，用户未见明确拍板记录，动手前问」**

已拍板且已落地。人原话（2026-11-21）："顺手把语音和手写砍了，只留文字"。
落地内容：`VoiceInput.kt` / `InkPad.kt` / manifest 的 `RecognitionService` 可见性声明全删，
5 张旧截图换成 6 张新截图，`copy-inventory.md` 同步。`BACKLOG` 头部与
`android-ui-handoff.md` §4.6（恢复条件）都有记录。
**这条错得最有害**：后来的 Agent 读到会重新问一遍，或以为功能还在，白花一轮。

### 2.3 表述过时

**③ §5「"整份不合格"的部分给分：倾向只计确定性断言判得死的部分…（代码已留切换位）」**

人已拍板选 B 口径（"只算机器判得死的那部分"），且核证结论比"留了切换位"更硬：
**当前没有过滤对象**——`rubric_credit` 的全部断言都由确定性执行器判（`file_exists` /
`json_field_equals` / `trace_param_schema_valid` / `trace_final_status`），A 口径与 B 口径在现有
判分项上恒等；因此用一条"将来若出现语义判定的 credit 项就会红"的守门测试表达，而不是写一个
不会被执行的空过滤。把已定的事写成"待确认"，会让下一个人重新拍一遍。

### 2.4 内部矛盾与失真

**④ §2**：先写「12 题 = 2 基座 + 10 变体；技能 3 个；错误类型 17 条」，末句「规模数字不在此写死，
用 §9 命令现场取」。同一段里自打嘴巴。这类矛盾在本仓库已经害人五次（用例数 1556→1580→1583→1588→1607
每次滞后一轮）。处置：数字保留但标注「2026-11-21 实测，随扩题变化」，把"不写死"改成"标明取样时点"。

**⑤ §9**：`verify.bat /nopause # 期待 RESULT: ALL GREEN、VERIFY_EXIT=0`。
`verify.bat` 只打印 `RESULT: ALL GREEN - claims verified.`（第 122 行），从不打印 `VERIFY_EXIT`。
正确的第二条判据是**退出码**：`RC=0`（`BACKLOG` C-01 的关单判据写的就是 `RC=0`）。

**⑥ §3.1**：只说 `PipelineError`，没给模块。它在 `src/arena/trace_pipeline.py:61`。
我按直觉去 `diagnosis_report` 里找，直接 `AttributeError`（见 §五）。不算错，算不给路。

**⑦ §6.3**：五份夹具写成「满分/缺数字/无产出/有答案无过程/假重试」。实际是
`raw-perfect` / `raw-empty`（空文件）/ `raw-no-file`（无产物）/ `raw-no-trace`（有答案无过程）/
`raw-fake-retry`（假重试），**没有"缺数字"这份**。且这五份不是散落脚本：
`fixtures/raw-*.json` 在仓库里，分数表由 `python -m arena.diagnosis_report --fixture all` 现场跑出，
评审包测试会解析该表（`SCORE_RE`）——dbg-001 这道**已被守卫锁住**，其余 11 道没有对应夹具。

### 2.5 规则与现实的冲突（要人拍）

**⑧ §3.9「main 只经 PR：不直推、不 force push」**

- 文档侧：`docs/COLLABORATION.md` §5.1 写「`main`：受保护，只经 PR 进入」，§5.3 规定 Squash and merge。
- 现实侧：`git rev-list --count HEAD` = **148**，`git log --oneline --merges` **空**（零合并节点），
  且提交是直推上去的（`b78cecb..18b8dd5` 直接落 main）⇒ main 上**没有**分支保护。
- 结论：这条规则是**两人协作期**（学生A 审学生B）的约定，当前是单人维护 + AI，没有第二评审人，
  实际从未执行。指南把它列进「违反=退回」的硬口径，等于给每个后来的 Agent 设了个必然违反的条款。

处置：**从硬口径挪到「待确认」**，硬口径里只留真的在执行的半句（不 force push、口径改动走登记流程）。
是恢复 PR 流程还是改成"直推 + 闸门即评审"，需人拍（见 §四）。

## 五、本轮我自己踩的坑（留痕）

  → `AttributeError`。真实位置 `trace_pipeline.py:61`。
  **教训**：指南类文档点名符号时，符号名不等于路径；核证时要么用 `grep -rn "class X"` 定位，
  要么把"没找到"当成"路径没写"，不要一上来就判文档错。

  **教训**：与 §7.4 同源——统计口径不一致时先查字段真名，再下结论。
