## 一、先把数字对齐（含两处需要你核对的地方）

### 1.1 你的数字自洽性【确】

- 全量 16 分钟 = 960 秒；1902 个用例 → 平均 0.50 秒/例。
- 文件 A：54 例 / 307 秒 = **32.0%**，与"占 32%"吻合。
- 文件 B+C：51 例 / 180 秒 → 平均 **3.5 秒/例**。
- 文件 A 里 20 个子进程用例，每个 5~21 秒。上界：20×21 = 420 秒 > 307 秒，所以**它们的总和落在 100~290 秒之间**（其余 34 例至少占 ~17 秒）。取中位估计 ~13 秒/个 → **20 个子进程 ≈ 260 秒，占文件 A 的 85%、占全量的 27%**。
- 扣掉子进程块后：**剩余 1831 个用例共约 700 秒，平均 0.38 秒/例**。

**推论【确】：耗时高度集中，不是均匀分布。** 你的"4~5 分钟"目标完全可达，因为绝大部分用例本来就已经很快。

### 1.2 并行单独达不到目标 —— 你的"省 8 分钟以上"估计漏了开销【确】

| 方案 | 理论下限 | 现实估计（含 Windows 开销） |
|---|---|---|
| 只并行，4 进程 | 960/4 = **4.0 分钟** | **5~7 分钟**（进程启动、每个 worker 各自重新 import + 收集、IPC、断言重写、收集阶段就是慢的部分） |
| 只并行，8 进程 | 960/8 = 2.0 分钟 | 3.5~5 分钟（边际收益递减，且 Windows 上进程创建开销线性上升） |
| 只去子进程（保留串行） | 960 - 247 = **11.9 分钟** | ~12 分钟 |
| **去子进程 + 4 进程并行** | 713/4 = **3.0 分钟** | **3.5~4.5 分钟** ✅ |
| 去子进程 + 6~8 进程并行 | 713/8 = 1.5 分钟 | 2.5~3.5 分钟（收益递减） |

**所以：你的"并行预计省 8 分钟以上"如果指"省掉 8 分钟"，那剩 8 分钟，达不到 4~5 分钟的目标；如果指"并行后剩 8 分钟"，同样达不到。** 两条路都得走。

**并行本身有一个容易被忽略的固定成本【推，高置信】**：xdist 的每个 worker 是一个独立进程（Windows 上是 spawn 语义，不享受 fork 的 COW 好处），**每个 worker 都要重新 import 全部测试模块并各自做一次收集**。你的 56 个测试文件如果 import 成本是 X 秒，那么 4 个 worker 就是 4×X 的 CPU 工作（墙钟上并行，但会挤占核）。这就是为什么"4 进程"比"理想 4 分之一"慢。

### 1.3 需要你核对的两处【需实测】

**(a) "77%" 这个数对不上其余数字。** 按你给的描述，慢用例 = 20（子进程）+ 51（DB）= 71 个 → 快用例 = 1831 个 = **96.3%**，不是 77%。慢用例占的时间是 487/960 = **51%**，也不是 23%。
→ 三种可能：(i) 你的快/慢划分比"子进程 + DB"这两组更大（还有 HTTP 服务那批你没给数量）；(ii) "77%" 指的是别的口径（比如文件数占比、或某次具体分组的比例）；(iii) 数字记错了。
→ **请核对**，因为"日常快跑"的具体命令行依赖这个划分。

**(b) 20 个子进程是不是每次都收集"整个测试套件"？** 这直接决定去重能省多少、能不能做。请看一眼那个子进程的调用：命令行大致是 `pytest --collect-only`（收集全仓）还是 `pytest <某个子目录>`（收集局部）？

## 二、排序后的前三条：做法 / 省多少 / 代价 / 验证方式

### 第一条：子进程收集去重为「每会话一次」

#### 2.1.1 为什么它排第一【确】

它是**唯一一条"省掉的时间与真实性完全无关"的路**：省下的是**重复劳动**（同一个数字被算了 20 遍），不是"少做了一次验证"。真子进程还在跑，数字还是来自一次真实的 pytest 收集。所以它既是最省时间的之一，又是风险最低的之一。

#### 2.1.2 推荐实现（三选一，按推荐度排序）

**方案 A（首选）：一次真子进程收集 → 产出一张 per-file 计数表 → 20 条断言都读这张表。**

- 用一个 **session 级 fixture**（放在 `conftest.py`）跑一次 `pytest --collect-only -q`（真实子进程），把输出按文件前缀解析成 `{文件路径: 数量}` + 总数，缓存到 session 作用域的对象里。
- 20 个测试用例改成读这张表并断言，**断言内容一字不改**（还是断言"评审包声称的数量 == 实际收集到的数量"）。
- 关键收益：**那个数字仍然来自一次真实运行**，只是"跑一次"而不是"跑 20 次"。

  ⚠️ **实现要点**：session 级 fixture **在 xdist 下每个 worker 各跑一次**（不是全局一次）。这是好事（并行），但配合 `--dist loadfile` 时那 54 个用例会落在同一个 worker → 只跑 1 个子进程。

**方案 B：进程内收集（`pytester`）。**
- `pytester` 是 pytest 自带的 fixture，用法是在 `conftest.py` 里 `pytest_plugins = ["pytester"]`。
- `pytester.runpytest_inprocess()` 在**当前进程内**跑一次真实的 pytest 收集，能拿到收集到的 item 列表（`pytester.getitems()`——这个 API 我**不能百分百确定各版本都有**，稳妥做法是从返回的 `RunResult` 的输出里解析 item id）。
- 优点：比子进程快一个数量级。
- 代价（**这就是我为什么把它排第二**）：进程内跑 pytest 有**状态泄漏**风险——`sys.modules` 污染、monkeypatch 未复原、全局状态（logging handler、缓存）残留。对"只做收集、不跑测试体"的场景这个风险很小，但比方案 A 大。
- 如果你用方案 B，**建议同时保留一个真子进程用例**当"真实性锚点"（那条用例必须真起子进程），其余 19 条走进程内表。

**方案 C：哈希缓存（你问的第三件事）。** 见 §4，结论是**不推荐**，除非你确实需要跨会话省那 5~21 秒。

#### 2.1.3 你的守卫不够，需要补两条【重要】

你写的是"如果收集阶段报错，必须失败，不能静默变成 0"。**这条挡住了"报错"和"空"，但挡不住"静默变成一个错误的非零数字"**——比如收集时某个文件 import 失败被跳过、或者路径写错导致只收集到子集，得到 1890 而不是 1902，测试照样绿。

建议守卫升级为三条：
1. **报错即失败**：子进程非零退出码 → 测试失败。（你的原守卫）
2. **数量合理域**：总数必须 `>= 1` 且落在你记录的 `[下限, 上限]` 内（例如 `[1800, 2000]`）→ 防止"静默变 0/变小"。
3. **交叉校验（最有价值）**：拿"本次会话自己收集到的用例数"（用一个 `pytest_collection_modifyitems` 钩子记下来）去比对子进程收集到的总数。**两者相等 ⇒ 这个数字确实来自一次真实收集，而不是抄来的、不是缓存的、不是手填的。** 这一条把你的测试从"数字对不对"升级成"数字的来源可证"。

#### 2.1.4 预计省多少【推】

- 子进程块总耗时 ~260 秒（区间 180~290），去重后剩 1 个子进程 ~13 秒 → **净省 ~247 秒 ≈ 4.1 分钟**。
- 保守区间：**3~4.5 分钟**。
- 若那 20 个用例原本就是收 20 个不同目录（§1.3(b)），去重收益下降，此时方案 B 才是主力。

#### 2.1.5 验证方式（怎么知道没改弱）

**验证 1：数量不变**。改动前后各跑一次 `--collect-only -q`，行数完全一致 = 1902。这是最硬的"没改弱"底线——**任何提速改动后，收集到的用例数必须仍是 1902**。

**验证 2：outcome 集合逐条一致**。改动前后各生成一份 junit XML，比较 (用例名, 结果) 的集合，必须完全相同（用例数不变 + 通过/失败/跳过状态不变）。命令：
```
python -m pytest --junitxml=before.xml
# 改动后
python -m pytest --junitxml=after.xml
# 比较（用一段 5 行的 python 脚本读两个 xml 对比）
```
Windows 上不要用 `diff`，用 Python 读 `xml.etree` 对比更稳。

**验证 3：变异测试（最关键）**。在一个**隔离副本**里故意删掉一个测试函数、或改一个函数名，然后跑那条自检用例 → **它必须失败**。如果删了用例它还绿，说明它没在真的收集，白花 4 分钟。
- 顺带：同一个副本里故意把子进程命令改成收集错误目录 → 用例必须失败（验证守卫 1、2 生效）。
- 再一个副本里把计数表改成硬编码常量 → 守卫 3（交叉校验）必须失败。

**验证 4：子进程确实只起了一次**。在子进程调用处打印/写一行到临时日志，跑完数一数行数 = 1。（这条是"真的去重了"的证据，防止你只改了断言没改 fixture。）

**验证 5：跑 20 次的耗时对比**。同一台机器，改动前后各跑文件 A，记录墙钟。

### 第二条：并行（xdist）

#### 2.2.1 为什么排第二而不是第一【确】

并行能带来的收益完全取决于**能并行的比例**，而你现在最大的那一块（260 秒子进程）被第一条吃掉了；并行本身在 Windows 上还有不可忽略的固定成本（进程启动 ×N、每 worker 重新 import + 收集）。**风险最高、收益依赖环境、最容易出现"跑得快但结果不可信"，所以不能当第一条做。**

但顺序不能反：**先做第一条再并行，是为了让你在并行后还有余量**（去子进程后 4 进程有 ~3.5~4.5 分钟的余量；先并行则可能卡在 5~7 分钟）。

#### 2.2.2 安装与依赖风险

**依赖**：`pytest-xdist`（会带 `execnet`）。
**你能装，但风险在这几处【推，中高置信】**：
- **Windows 防火墙弹窗**：xdist 的 worker 通信走 execnet，会在 127.0.0.1 上开随机端口监听；Windows 首次可能弹防火墙询问。弹了就允许，或把 Python 加进白名单。**如果这个弹窗在 CI/日常里反复出现会很烦**——这是"能装但有摩擦"的一条。
- **不改变断言语义**：xdist 只是多进程调度器，不改测试语义。**前提**是测试之间真的互相独立（见 §3）。
- **不要与随机顺序插件共存**：如果环境里装了 `pytest-randomly`（它会打乱顺序），并行下会让顺序依赖的测试随机失败。检查：`pip list | findstr pytest`。禁用：`-p no:randomly`。

#### 2.2.3 起步命令

```
python -m pytest -n 4 --dist loadfile
```
- `-n 4`：先从 4 开始，不要直接 `-n auto`（auto 按 CPU 数，在笔记本上常常给出过多进程，反而更慢）。
- `--dist loadfile`：**同一文件的所有用例放同一个 worker**。这对你至关重要——文件 A 的 54 个用例共享一个 session fixture（去重后的那一次子进程），`loadfile` 保证它们只跑一次子进程。默认的 `load` 分配方式会把它们拆散 → 多个 worker 各自跑一次子进程，白白浪费。
  - 备选 `--dist loadscope`（按类/模块作用域分组），如果你有类级 fixture。**具体行为以你环境里 xdist 的帮助文本为准**（`pytest --help | findstr dist`），我不给版本号。

#### 2.2.4 预计省多少【推】

- 前提：先做完第一条（剩 ~713 秒可并行工作量）。
- 4 worker：理想 178 秒 + 开销（进程启动、每 worker 收集、IPC）→ **现实 3.5~4.5 分钟**。
- 6~8 worker：可能到 2.5~3.5 分钟，但 Windows 上进程创建和内存压力开始反噬。**4~6 是甜点区**。

#### 2.2.5 验证方式

**验证 1：结果一致性**。你说的"并行下全量跑两次结果一致"——方向对，但要具体化：
```
python -m pytest -n 4 --dist loadfile --junitxml=par1.xml
python -m pytest -n 4 --dist loadfile --junitxml=par2.xml
```
比较 par1/par2 的 (用例名, 结果) 集合 → 必须完全相同；再与**串行**跑出的 `before.xml` 比 → 也必须完全相同。**注意 xdist 的 junit XML 里用例顺序可能不同，比较时要用集合比较而不是顺序比较。**

**验证 2：数量守恒**。xdist 的汇总行报的通过数必须 = 1902（减去 skip/xfail 的差值）。少一个用例 = 有用例在并行下被吞了，这是最常见的静默故障。

**验证 3：跑 3 次**，不只是 2 次。并行下的偶发干扰往往第 3 次才出现。

**验证 4：变异测试在并行下也要红**。在隔离副本里制造一个失败用例，确认 `-n 4` 下它确实报红（而不是被吞）。

**验证 5：真实计时**。同一台机器、同一时段，串行 vs `-n 4` 各跑 2 次取最好成绩。**别用第一次跑的成绩**（冷缓存、AV 扫描、CPU 降频）。

### 第三条：临时 SQLite 调优

#### 2.3.1 先测量，别先改【需实测】

51 个用例 180 秒 = **3.5 秒/例**。这个数对"建库 + 灌几条记录 + 算分 + 查"来说**偏高**。但高在哪，只有测了才知道：

```
python -m pytest --durations=30 --durations-min=0.5
```
`--durations` 按耗时排序列出最慢的 30 个用例，`--durations-min` 设门槛。**这 30 行几乎一定直接告诉你答案**：是连接建立慢、是 schema 初始化慢、是 INSERT 慢、是"算分"慢、还是 fixture teardown 慢。

> 我的判断：**3.5 秒/例多半不是 SQLite 的 IO 慢，而是"逐条 INSERT（每次自带一个事务）"或"fixture 每次重建 schema"或"算分逻辑 O(n²)"**。SQLite 在本地磁盘上插几百条记录是毫秒级的。

#### 2.3.2 三档改法，按风险从低到高

**档 1（零风险）：改写入方式，不改 SQLite 行为。**
- 把逐条 `execute` + `commit` 改成 `executemany` + **一次** `commit`（一个事务里批量写）。这是纯粹的减少事务开销，**不改变任何语义**。
- 查证 SQLite 库里这些记录的写入语义有没有依赖"每条提交"（比如测的是崩溃恢复）→ 如果有，别改。

**档 2（低风险）：连接级 PRAGMA，只在测试库上开。**
```sql
PRAGMA journal_mode = OFF;   -- 或 MEMORY
PRAGMA synchronous = OFF;
PRAGMA temp_store = MEMORY;
PRAGMA cache_size = -64000;  -- 64MB
```
- **代价要说清楚**：这些关掉了**持久性/崩溃安全**。如果被测代码里有一条用例专门测"写了一半进程被杀 → 数据还在吗"，那它就**失效了**（测弱了）。这属于"不许把测试改弱"的边界，必须由你判断有没有这种用例。
- **只对测试用的临时库开**；绝不能影响生产路径。

**档 3（中风险）：换 `:memory:` 库。**
- **前提**：被测代码接受一个"已打开的连接"或"数据库路径"作为参数。多数代码是"按路径打开"→ `:memory:` 根本用不上（每个连接一个独立内存库）。
- **代价【推】**：一旦被迫改生产代码的接口（让它接受连接对象），你就**改了被测代码的形状**——这会把"测试适配"混进生产代码，风险和收益都要重新算。**我的建议是别走这条**，除非你的代码本来就有连接注入点。
- 另外，内存库**测不出文件锁、文件路径、权限、磁盘写满**这些真实行为——这也是"改弱"的一种。

#### 2.3.3 另一个可能的大头（你提的 HTTP 服务那批）

- 【需实测】数量未知。如果这批也在几十秒量级，值得单独看。
- **可选优化**：把 HTTP server 做成 **module 级 fixture**（一个模块起一次服务），每个用例只重置状态。
- **代价**：共享服务 = 状态泄漏风险（上一个用例污染下一个），可能让某些用例"意外通过"→ **这正是改弱**。所以共享服务器的 fixture 必须是"起一次服务 + 每例重置到干净状态"，而不是"起一次服务 + 随便用"。**这条要你逐个用例检查，不是无脑共享。**

#### 2.3.4 预计省多少【推，不确定】

- 档 1（批量写 + 一次提交）：**30~90 秒**。
- 档 2（PRAGMA）：再加 **10~60 秒**。
- 合计**乐观 1.5 分钟，保守 0.5 分钟**。**在 `--durations` 出来之前，这个数字我不背书。**

#### 2.3.5 验证方式

- `--durations` 前后对比，看这 51 个用例的总耗时下降。
- **行为等价性**：对同一个场景，用"旧写法"和"新写法"各建一次库，把**所有查询结果**（不只是主结果）做逐行比对——用 `iterdump()` 或逐表 SELECT 后比对。这条能挡住"为了快把某个字段写错/少写"的改弱。
- 变异测试照旧。

## 三、并行在这个场景会撞的坑（每条：现象 → 原因 → 规避）

按"发生概率 × 破坏力"排序。

### 坑 1：嵌套 pytest 子进程在 xdist 下行为异常（最可能先撞上的）

- **现象**：加了 `-n 4` 之后，那 20 个子进程用例挂住、或报奇怪的错、或返回 0 个用例。
- **原因【推，高置信】**：xdist 会给 worker 进程设置 `PYTEST_XDIST_WORKER` / `PYTEST_XDIST_WORKER_COUNT` 之类的环境变量；**你起的嵌套 pytest 子进程会继承这些环境变量**，于是它以为自己是 worker，会去找一个并不存在的控制器 → 挂住或行为异常。同类问题：`PYTEST_ADDOPTS` 里如果带了 `-n`，会被子进程继承，导致子进程也想开并行。
- **规避**：
  - 传给子进程的环境**显式剔除** `PYTEST_XDIST_WORKER`、`PYTEST_XDIST_WORKER_COUNT`；把 `PYTEST_ADDOPTS` 覆盖为空再显式传你想要的参数。
  - 或者子进程加 `-p no:xdist`（禁用 xdist 插件）。**这个参数名我不给版本号，以你环境里 `pytest --help` 为准。**
  - 或者干脆用方案 A 的语义：**在 xdist 下干脆不要用子进程**（改进程内收集）——但这就回到 §2.1.2 的方案 B 的真实性权衡了。
  - **验证**：`-n 4` 下单独跑文件 A 的那 20 个用例，必须全绿且**每个 worker 只起 1 次子进程**（配合 `--dist loadfile`）。

### 坑 2：临时 SQLite 文件撞名 → "database is locked" / 数据串了

- **现象**：并行下偶发 `sqlite3.OperationalError: database is locked`，或某个用例读到了另一个用例的数据。
- **原因**：如果临时库用固定文件名（比如 `tmp.db`、`test.db`、放在当前工作目录），多个 worker 会写同一个文件。Windows 上文件锁语义更严格，更容易暴露。
- **规避**：
  - 用 pytest 内置的 `tmp_path`（每个用例独立目录，天然不撞）；或 `tmp_path_factory`。
  - ⚠️ **注意 `tmp_path_factory.getbasetemp()` 的基目录在 xdist 下是共享的**，如果你在里面按 `db_0.sqlite` 这种"自己编号"的方式建文件，仍然会撞。要么用 `tmp_path`（每例独立），要么文件名里带 worker id / PID / uuid。
  - **验证**：`-n 4` 连跑 3 次，且刻意让多个用例同时写库。

### 坑 3：随机端口撞车

- **现象**：`Address already in use` / `OSError: [WinError 10048]`。
- **原因**：如果你的做法是"先随便取一个端口 → 关掉 socket → 再用这个端口起服务"，中间有一个空窗期，并行会把这个窗口的碰撞概率放大。
- **规避**：
  - 让内核分配端口：绑定 `0`，然后从 `server.server_address` 读回实际端口（socket 保持打开直到服务就绪）。**这是"先占后读"，没有空窗期**，并行下最稳。
  - 保留 `SO_REUSEADDR`（Windows 上语义与 Unix 不同，注意别依赖它解决 TIME_WAIT）。
  - **验证**：`-n 6` 下跑端口相关的用例 5 次。

### 坑 4：跨文件的顺序依赖被打乱

- **现象**：串行全绿，并行偶发失败，且失败用例"随机"。
- **原因**：xdist 保证**同一个 worker 内的执行顺序**（`--dist loadfile` 下同文件顺序也保持），但**不同文件之间的相对顺序不保证**。
- **规避**：
  - 定位：失败后用 `-n 0`（或去掉 `-n`）单独跑那个用例 → 如果单独跑绿、并跑红，几乎可以确定是文件间顺序依赖。
  - 修法：把有依赖的文件用 `--dist loadfile` 归到同一 worker（如果它们文件名上有约定，比如 `test_a_step1.py` / `test_a_step2.py`，xdist 不保证同前缀同 worker——**更稳的是把它们合并成一个文件，或用 `@pytest.mark.xdist_group`（标记名我不给版本号，以帮助文本为准）**）。
  - **验证**：串行 vs 并行的 outcome 集合必须完全一致（§2.2.5 验证 1）。

### 坑 5：每个 worker 重复做收集/导入（性能，不是正确性）

- **现象**：`-n 8` 反而比 `-n 4` 慢；或启动后有一段"卡住不跑"的时间。
- **原因**：每个 worker 是新进程，重新 import 全部测试模块 + 各自收集一次。56 个文件的 import 成本 × worker 数。
- **规避**：先测 `-n 2 / 4 / 6` 的实际墙钟，取最优；把重依赖的 import 尽量放进 `conftest.py` 的 session 作用域或延迟导入；确认没有"每个 worker 都要联网/编译/生成大文件"这类操作。

### 坑 6：断言重写与插件状态的每 worker 重复成本

- **现象**：`-n` 越大，固定开销越明显。
- **规避**：不为此关闭断言重写（那会**丢失断言失败详情**，是诊断能力损失）；如果实在要，**只在这一条命令上加 `--assert=plain`**，别写进默认配置。

### 坑 7：xdist 下"统计总数"的用例语义漂移

- **现象**：某个断言"总数等于 1902"的用例，在 `-n 4` 下读到别的数。
- **原因**：如果你那个用例是通过"看当前 pytest 进程的收集数"实现的，xdist 下各 worker 的收集范围可能与控制器不同。
- **规避**：用 §2.1.2 方案 A 的"独立子进程收集 + 交叉校验"结构，把"本次会话收集数"与"独立子进程收集数"分开断言。

### 坑 8：并发下共享的临时目录/缓存目录/日志文件互相覆盖

- **现象**：日志里少了某些用例的记录；或缓存文件损坏。
- **规避**：所有"跨用例共享的可写文件"必须按 worker/用例唯一命名，或干脆放进 `tmp_path`。

## 四、"既保留真实性、又不用每次真跑"——缓存方案的评估（你问的第三件事）

### 4.1 结论先说【确 + 推】

**不推荐跨会话的哈希缓存来缓存"用例数"。** 理由：

1. **收益极小**：省的就是那一次子进程（5~21 秒）。
2. **风险不小**：失效判断一旦漏一项，就是**静默地用一个过期的数字通过测试**——这比"慢 15 秒"糟糕得多，而且这种错**不会自己暴露**。
3. **有更优替代**：§2.1.2 的方案 A（**每会话跑一次真子进程**）既省掉了 19/20 的重复，又**完全没有缓存过期问题**。真子进程每会话跑一次，本来就不需要缓存。

**只有当你的场景是"这个自检每天跑很多次（CI 上多分支/多环境/多配置）"时，跨会话缓存才值得考虑。**

### 4.2 如果你坚持要做缓存：失效条件清单

**缓存键（key）必须包含**：
1. **所有可被收集的测试文件的 (相对路径, 内容 sha256) 的排序列表** —— 这一条就解决了你说的"识别用例被删了/改名了"：
   - 改名 → 路径变了 → 键变 → 失效 ✓
   - 删除 → 列表变短 → 键变 → 失效 ✓
   - 内容改（哪怕只改了个断言）→ 键变 → 失效 ✓
2. **所有 `conftest.py`**（含子目录的）—— conftest 决定收集逻辑。
3. **ini 配置**：pytest.ini / pyproject.toml 的 `[tool.pytest.ini_options]` / setup.cfg / tox.ini（你说没有，但键里留着，防止以后加上）。
4. **Python 版本 + 实现**（`sys.version_info`）、**pytest 版本**、**已安装插件及版本列表**。
5. **平台**（`sys.platform`）—— 收集期的 `skipif` 在不同平台产生不同数量。
6. **本次的筛选参数**：`-k` / `-m` / `--ignore` / `--ignore-glob` / `--deselect` / `-p` —— 不同筛选下的数量根本不同。
7. **收集逻辑读取的外部资源**：如果收集依赖某个配置文件、数据库、生成的目录，**这些也必须进键**。

**会导致"键没变但数字其实变了"的漏判（危险）**：
- 收集逻辑读取了**未进键**的外部文件（配置/DB/生成物）。
- `parametrize` 的取值来自**环境变量**或**外部数据**（键里没有）。
- `parametrize` 或收集依赖**当前时间/日期**（同一天同文件，数字可能随时间变）。
- 新装/卸载了**插件**（插件可以自己加用例）→ 键里必须含插件列表，否则漏判。
- 收集依赖**被测代码的运行时行为**（极少见，但"生成式测试"会这样）。

**会导致"键变了但数字没变"的无害重算（只是浪费一次）**：
- 改了注释、格式化、换行 → 键变 → 重算 → 数字一样 → 通过。**这是可接受的假失效**，代价只是几秒。

### 4.3 缓存命中时仍然必须做的三件事（否则缓存就是在造假）

1. **廉价断言不能省**：总数 `>= 1` 且在合理区间内 —— 挡住"缓存文件损坏/写成了 0"。
2. **强制真实跑的开关**：比如环境变量 `REAL_COLLECT=1` 时无视缓存，每次都真跑；给你一条"我不信缓存"时的验证命令。
3. **缓存文件不入库、不进 CI 产物**；写它的地方要保证并发写不互相覆盖（多个进程同时写同一个缓存文件 → 读到半个文件）。缓存文件写到 `tmp_path` 或带进程唯一后缀。

### 4.4 关于"不要用数字本身做键"

用"用例总数"做缓存键 = 自证（总数没变 ⇒ 缓存命中 ⇒ 断言总数相等 ⇒ 通过）。**必须用文件树哈希。** 你想到"按文件内容哈希缓存"这个方向是对的。

### 4.5 如果你真的只是想让"改弱"被发现，有个更简单的办法【推】

**不改任何东西，把"收集数"写成一个每次运行都真跑一次的形式**（方案 A），再加一条**变异测试作为守卫**：
> 在 CI/提交前的一个隔离副本里删掉一个测试 → 那条自检必须失败。

这样你不需要缓存，也不需要复杂的失效条件，真实性反而更强。

## 五、我认为你**不该**做的优化，以及理由

| 不该做 | 理由 |
|---|---|
| **把子进程收集换成 mock / 假装收集** | 直接违反你"不许把测试改弱"的红线。而且那条用例的**职责本身就是**"证明这个数字来自真实运行"。mock 掉等于把被测对象删掉还宣布测试通过。 |
| **把"计数"改成从某个生成文件 / 缓存 / 常量里读** | 同上，而且更隐蔽——它看起来仍然"跑了一个子进程"，但数字是抄来的。 |
| **用 `skip` / `xfail` 把慢用例"处理掉"来让全量变绿** | 这是最典型的"改弱"。`xfail` 会让用例失败时也不报红，红灯变绿灯。 |
| **用 `-m "not slow"` 的结果代替全量结果** | 日常可用，**不能作为"全绿"的证据**。慢用例正是最容易暴露真实缺陷的那批。 |
| **为了让并行不撞车而给用例加 skip** | 同上，且是隐蔽的：用"跳过"换"不失败"。 |
| **把 HTTP 请求改成 mock**（为了省端口/时间） | 那就测不到真实的 socket/编解码/超时路径。你已经为了真实性在做真请求，别在这里退回去。 |
| **改生产代码接口（让它接受 connection 对象）以便用 `:memory:`** | 为了测试方便改被测代码的形状，风险扩散到生产路径；且内存库测不出文件锁/权限类行为。 |
| **关闭断言重写 / 关插件** 来提速 | `--assert=plain` 丢的是失败详情（诊断能力，不是测试强度）；关插件可能改变收集或行为。**可以临时在命令行加，不要写进默认配置。** |
| **把 Windows 杀毒排除整个项目目录写成默认设置** | 这是**降低你机器整体安全性**的取舍，不是测试优化。可以做，但应该是你明确知情的一次性决定，且范围尽量小（只排 temp 目录，别排整个仓库）。**我不会把它列为推荐项。** |
| **接受"并行跑两次结果一致"作为唯一验证** | 两次一致不能证明"没有系统性地一起错"（比如两个 worker 都用了同一个共享坏文件）。**必须和串行结果比**，而且要有变异测试。 |
| **相信"我以前从没遇到过"＝不存在** | 顺序依赖、端口撞车这类问题在单进程下几乎必然不出现。**并行会暴露它们，而不是制造它们。** |

## 八、总结：建议的执行顺序

| 顺序 | 动作 | 预计耗时 | 累计总时间 | 风险 |
|---|---|---|---|---|
| 0 | **跑 `--durations=30`**，看清每个慢用例慢在哪 | 16 分钟（一次） | — | 无 |
| 1 | **子进程收集去重为每会话一次** + 补三条守卫 + 变异测试验证 | 1~2 小时（含验证） | **~12 分钟** | 低 |
| 2 | **只做 SQLite 档 1（批量写 + 一次提交）**，用 §2.3.2 的等价性比对验证 | 1 小时 | **~11 分钟** | 低 |
| 3 | **并行 `-n 4 --dist loadfile`**，串行 vs 并行 outcome 集合比对 + 变异测试 | 半天（含踩坑） | **~4~5 分钟** ✅ | 中 |
| 4 | **日常快跑 + 提交前全量**（强制执行，不靠自觉） | 半天 | 总时间不变，等待变少 | 无 |
| 5 | （可选）SQLite 档 2 PRAGMA / HTTP server 复用 / Windows AV 范围 | 按需 | — | 低~中 |

**第 3 步是唯一有"踩坑"成本的步骤，但它也是唯一把你送进 4~5 分钟的步骤。第 1 步做完你就已经省了 1/4 的时间，而且这一块是纯重复劳动。**
