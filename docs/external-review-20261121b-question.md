## 一、可直接复制的提问（复制这一段就够）

```
我在做一个编程训练器，本地运行不联网。想请你批评它的「题目内容」，不是代码。

【产品】学生领一道有 bug 的编程题，写代码跑出结果，并把执行过程记录下来提交。系统按预设的
检查项判分，产出一份诊断报告：错在哪一项、属于哪类错误、下次该练什么。系统把结果折成
三个技能的熟练度，据此推荐下一道题。最后要求用户用自己的话复述解题思路（这一步不判分）。

【规模事实，都可自查】
- 代码：约 14000 行 Python + 一个 Android 前端三页 + 1600 多个自动测试。
- 题目：12 道。
- 技能：只有 3 个（多步规划、工具参数校验、失败重试）。
- 判分项：每道题都是同样 5 项（2 个前提检查 + 3 个得分项），12 道题的区别是「期望答案的数字」
  和「故障出现在第几页」这类参数。
- 场景：12 道题挂在 2 个基座上，其中 10 道共用同一个模板（含那个基座）。它们**对外显示的业务名字不同**
  （交易流水、货品流水、采购入库、退款单、销售订单、批量订单……），但判分项和题目结构都继承
  同一个基座，实际差别是期望值和故障位置（比如页数上限 5 改成 4、故障从第 3 页挪到第 4 页）。
- 区分度实测：只在第一道题上做过，用 5 份不同质量的假提交跑出 0 / 0.25 / 0 / 0 / 1.00 的分数。
  其余 11 道题没有做过同类实验。

【我现在的困惑】
1. 这 12 道题其实算几道题？如果「换场景 + 换期望值 + 换故障位置 + 判分项不变」就算一道新题，
   那我已经有 12 道；如果要求判分项也跟着变，那可能只有 1-2 道。
   （澄清：判分项的 ID 和类型确实完全相同，但同一个判分项内部能分辨多种错误类型，见第 3 问，
   所以这里说的「不变」是指结构没变，不是判分能力粗糙。）
   请给一个可判定的标准：什么样的改动才算「一道新题」，而不是「同一道题换了个壳」？
   另外，12 道题里只有 1 道做过「区分度」实验（用 5 份不同质量的提交跑出不同分数），
   剩下 11 道没做过。一道题要算「验过了」，需要多少次、什么质量的提交？
2. 3 个技能是不是太粗？熟练度是每个技能一个数，现在用户的画像只有三个数字。
   技能该按什么切？按错误类型切、按知识点切、还是按「这题要用到哪些能力」切？
   在只有 12 道题、单用户的情况下，技能切成 10 个和切成 3 个，哪个更有用？
3. 判分能说对「哪一类错」，但说不出「错在哪」。实测：学生把每页条数写成 10（上限是 4），
   系统准确判出「参数越界」并归到正确的技能，机器可读的细节也有「10 > 上限 4」。
   但报告里**没有一句话**把这两者连起来讲给学生听——只有结构化的标签和数字，
   人话要页面自己拼。我该在哪一层补这句话：给每类错误写一句通用模板（17 类，不随题目增长），
   还是给每道题单独写（随题目数增长）？两种做法的维护成本和表达力怎么权衡？
4. 我准备把题从 12 道扩到 40 道左右，但有个硬约束：报告里每个字都必须能追到「题目定义」
   或「错误类型词表」，不许自由发挥，否则报告会变成编造。这个约束下，扩内容的成本大概
   是多少？哪些部分可以交给 AI 批量写而不破坏这条约束，哪些必须人写？
   我猜「人话那段」可以按错误类型写而不是按题目写，这样加题不必重写人话——这个思路对不对？
5. 我自己写的工具证明我自己通过（1600 多个测试、评审包、存档的测试记录都是我自己产出的）。
   如果你只能做一件事来独立验证这个系统，你会检查什么？请给具体动作，不要给原则。

【要求】
- 区分「事实」「行业常见做法」「你的推测」，不要混在一起说。
- 不要编造版本号、论文标题或 API 名，引用方法给可检索的名称即可。
- 如果我的某个前提就错了（比如「12 道题太少」这个判断本身），直接说错在哪，不用照顾我。
- 不需要读我的代码，上面的数字就是全部输入。
```

## 二、事实快照（每条都有复核命令）

### 2.1 规模

| 项 | 值 | 复核 |
|---|---|---|
| 提交数 | 147 | `git rev-list --count HEAD` |
| Python 模块 | 32 个，13990 行（`src/arena/`） | `wc -l src/arena/*.py \| tail -1` |
| 自动测试 | 1607 条，全绿（干净树 797.3 秒） | `pytest tests -q`；档案 `docs/test-evidence/INDEX.md` |
| 任务 | 12 个 YAML | `ls tasks/*.yaml \| wc -l` |

| 错误类型 | 17 条，其中 **4 条未映射任何技能** | 同上 |

### 2.2 任务库的真实结构（这节是本次外评的核心发现）

12 个任务**合并继承后每个都是同样的 5 个判分项**：

```
R1_file_exists          前提：产出文件存在
R5_clean_exit           前提：进程正常退出
R2_report_correct       得分：报表数字对
R3_retry_evidence       得分：失败重试有记录
R4_no_param_hallucination 得分：参数没有瞎编
```

对比四个不同「专项」的任务，判分项 ID 与类型几乎逐字相同（只有 `fix-001` 把
`R2_report_correct` 改名为 `R2_diagnosis_correct`）：

| 任务 | 族 | 判分项 |
|---|---|---|
| `dbg-001-order-report` | 调试向（基座） | R1 / R5 / R2_report_correct / R3 / R4 |
| `prm-003-page-ceiling-4` | 参数专项 | R1 / R5 / R2_report_correct / R3 / R4 |
| `ret-002-second-page-fault` | 重试专项 | R1 / R5 / R2_report_correct / R3 / R4 |
| `fix-001-token-expiry` | 定位向（基座） | R1 / R5 / R2_**diagnosis**_correct / R3 / R4 |

任务族（调试向 / 参数专项 / 重试专项 / 定位向）的差别落在两处：**期望答案的值** 与
**故障注入的位置**；判分结构不变。

### 2.3 继承关系

| 基座 | 继承它的任务 | 合计 |
|---|---|---|
| `dbg-001-order-report` | `dbg-002/003/004`、`prm-001/002/003`、`ret-001/002/003`（9 个） | 10 个任务 |
| `fix-001-token-expiry` | `fix-002`（1 个） | 2 个任务 |

即：**12 道题 = 2 个基座 + 10 个变体**。

变体的差异都在参数层，业务名称各不相同但结构与判分项继承基座：

- `prm-001/002/003`：交易流水（页上限 5）／货品流水（页上限 5 · 长数据）／采购入库（页上限 4）
- `ret-001/002/003`：退款单（故障码 503）／销售订单（故障在第 3 页）／批量订单（故障在第 4 页）
- `dbg-002/003/004`：发票金额／采购单金额／传感器批数据

**这是本节最需要外评判断的一点**：标题换了业务名，看起来是 6 个不同场景；
但判分项、题目结构、技能映射都继承同一基座。对外呈现「12 道题」与实质「2 套结构 × 参数」
之间的差距，是否构成对使用者的误导，我自己判断不了。

### 2.3.1 错误类型与技能的对应

17 条错误类型中 **4 条未映射任何技能**，且这 4 条恰好都是「前提失败」类：

```
no_output_file / empty_output_file / task_crashed / task_timeout
```

不映射技能在语义上说得通（学生没产出，谈不上哪个能力不足），但代价是：
这类判定出来后**无法绑定技能**，报告里「归因到技能」那一步是断的。

### 2.4 参数越界实测（2026-11-21 新增，推翻了我自己的怀疑）

原本我怀疑「参数专项」任务判不到点上：它的判分项 ID 与通用任务逐字相同，没有一条专判
「每页条数有没有超上限」。为了验证，做了一次实验。

**方法**：把 `dbg-001` 的满分提交原样丢给 `prm-003`（页上限 4）。该提交的轨迹里 `limit` 一律是 10，
因此在 `prm-003` 下每一次调用都越界。断言结果用系统自己的执行器现算，不手填。

**结果**：

| 观察点 | 实际输出 |
|---|---|
| R4 断言 | `fail`，违规明细 `{"param": "limit", "kind": "out_of_range", "detail": "10 > maximum 4"}` |
| 归因技能 | `tool_param_validation`（工具参数校验），**正确** |
| 归因错误类型 | `param_out_of_range` → 显示名「参数越界」，**正确** |
| 未归因项 | `[]`（全部归因成功） |
| 五条断言的人话说明 `note` | **全部为 `null`** |

**结论**：

1. **判分与归因是准的**——我原来的怀疑错了。判分项 ID 虽然相同，但错误类型检测规则按类匹配
   （四种参数错误各有分支），所以能精确说出「参数越界」并绑到正确技能。这一条不必再问外评。
2. **缺口在人话**：报告有结构化的结论（哪类错、哪个技能、`10 > maximum 4` 这种数据），
   但没有一句话把它们连成学生能读的句子。页面只能拿 `pattern_id` 去词表查标签，
   查不到就直接显示断言 ID——这正是复述页里「报告没给期望/实际」的来源。
3. **这个缺口可以低成本补**：不缺数据，缺「拼接规则」。按错误类型写 17 条模板即可，
   不必按题目写。这是本次外评想问的第 3 个问题的由来。

**复现要点**（脚本是一次性诊断，未入库；若要长期复核应固化为测试）：

1. 取 `fixtures/raw-perfect.json`，把 `submission.task_id` 改成 `prm-003-page-ceiling-4`，
   删掉自带的 `assertion_results` 与 `trace_audit`；
2. 用 `diagnosis_report.load_task()` 取**合并后**的任务（变体任务必须合并 `base_task`，
   否则读不到 `trace_requirements`、也读不到 `limit` 的 `maximum: 4`）；
3. 逐条调 `assertion_evaluator.evaluate_assertion()` 现算断言，`schemas` 用
   `load_tool_schemas('tools', task=task)` 传已合并的任务（不传就回退读默认 YAML，
   会拿到 `dbg-001` 的 `limit` 无上限版本，实验就白做）；
4. 把结果塞回 `assertion_results`，再 `build_report()`。

第 2、3 步是两个容易踩空的点：漏传合并后的 task，实验会静默变成「用错题目测」。

## 三、我自己拿不准的五点（含倾向与「什么会让我改主意」）

### 3.1 「12 道题」这个数字有多少水分

- **事实**：10/12 继承同一基座（业务名不同，判分项逐字相同）；差异在期望值与故障位置。
- **我的推测**：这更像「1 套判分模板 × 12 组参数」，而不是 12 道题。若真按「判分项也得变」算，
  独立题量约 2 道。
- **什么会让我改主意**：如果变体确实改变了**学生要做的事**（而不只是数据不同），比如
  「页数上限 4」逼迫学生发现边界条件而不是照抄上一题的代码，那它就有独立价值。
  这一点我自己判断不了，需要看真实学生的错误分布——现在没有数据。

### 3.2 判分说对了「哪类错」，但说不出「错在哪」（已实测）

- **事实**（§2.4）：参数写超上限时，报告准确归因「参数越界 + 工具参数校验」，
  并带「10 > maximum 4」的机器可读明细；但五条断言的 `note` 全为 `null`，页面拿不到一句人话。
- **我原来的判断是错的**：我曾怀疑「判分项不随题型变化」会导致归因错位
  （把「参数写超」说成「重试记录不全」）。实测不成立——判分项 ID 虽相同，但错误类型检测
  有四条分支，能分辨「越界 / 幻觉 / 漏传 / 类型错」。这条不该再麻烦外评。
- **我的推测**：缺的是「按错误类型写拼接模板」这一层。17 条模板各一句，可跨题复用；
  若按题目写，成本随题量线性增长，每加一道题都要重写一遍人话。
- **什么会让我改主意**：如果某类错误的明细数据本身不足以拼出人话（比如「总额算错」只有
  两个数字，说不出「哪一步漏算」），那光加模板不够，得回判分层补数据。
  这一点我还没逐类核查——**这是本次唯一想请外评给判断的地方**。

### 3.3 3 个技能撑不起一个用户画像

- **事实**：熟练度每技能一个数，共 3 个数；17 条错误类型里 4 条未映射技能
  （且都是前提失败类，见 §2.3.1，这四条判出来后无法绑定技能）。
- **我的推测**：3 个技能上做推荐，等于用一个三档量表指导教学，信息量太低；但盲目扩到 20 个技能
  会让每个技能都没有足够观测（12 道题分不到 20 个技能上）。
- **什么会让我改主意**：如果有「技能粒度 ↔ 每题观测数」的经验比例（如每个技能至少 3 道题覆盖），
  那就能反推技能数的上界。这个比例我不知道。

### 3.4 扩内容的成本与「不许编」的冲突

- **事实**：硬约束是报告每个字必须追到题目定义或错误类型词表；现有 12 道题是人写的。
- **我的推测**：可外包给 AI 的是「场景描述、期望值计算、错误类型命名」；不可外包的是
  「判分项到底考验什么」——后者决定题目有没有教学价值。
  另外按 §2.4 的发现，「人话那段」应挂在**错误类型**上（17 条，一次性）而不是挂在**题目**上
  （12 道且会增长），这样加题不必重写人话。
- **什么会让我改主意**：如果有办法把「判分项设计」也变成可验证的过程（比如先写「学生可能怎么错」，
  再据此写判分项），那外包范围可以扩大。

### 3.5 自证循环

- **事实**：除假提交外，所有「正确性证据」都由我自己的工具产出。
- **我的推测**：外部最低成本的验证不是复跑 1607 个测试，而是**挑一份假提交，手工核对报告**。
  如果报告说的和手工核的不一致，说明判分有问题；如果一致，说明这一条链可信。
- **什么会让我改主意**：如果外评指出更便宜的办法（比如只验 1 个断言的真假），我换。

## 四、已经排掉的选项（免得重复建议）

上一轮外评（2026-11-21）提过、我已核证后否决或暂缓的：

| 建议 | 处置 | 依据 |
|---|---|---|
| 换贝叶斯知识追踪（BKT）替代 EMA | **否决** | 每技能 4 参数、需大量观测序列；12 道题 / 单用户下可识别性无法论证，且标签会被事后仲裁改写，违反「观测噪声平稳」假设 |

| 「缺失项被算成正证据」 | **前提不成立** | 缺失项权重 0，只累加覆盖项，从不相加 |
| 砍掉复习排程层（「没消费者」） | **否决** | 排程建议读 `1-P` 与 `1-R` 作因子，消费者存在；缺的只是 Android 提醒页 |

用户可见文案总表 153 条 + 一致性校验、复述页改为「先交后看」。

## 五、内部记录：准备这份材料时我自己犯的三个错

写材料过程中先算错两次、判断错一次，都记下来，免得下次重犯：

1. 用 `yaml.safe_load` 直读任务文件统计判分项，得出「有的任务只有 1 条判分项」，
   据此准备写「1 条判分项判不出东西」。**错**：那是任务自己覆盖的部分，合并 `base_task` 后
   每个任务都是 5 项（2 门禁 + 3 积分，共 60 条）；正解要用 `diagnosis_report.load_task()`。
2. 同一错误导致「12 个任务 60 条断言」与「每任务 1-5 条」两个数字并存过一阵，属自相矛盾；
   已用合并后的统计统一为「每任务 5 项」。
3. **判断错**：我原本断言「判分项不随题型变化会导致归因错位」，并准备把它作为第二个问题发给外评。
   实跑一次（§2.4）发现归因完全准确——判分项 ID 相同，但错误类型检测按类分支，
   能分辨越界/幻觉/漏传/类型错。**如果直接发出去，会让外评花一整轮批评一个不存在的问题。**

教训写在这里而不是删掉：

- **统计口径不一致时，先核对「继承/覆盖」这类机制，再下结论**；
- **怀疑某个环节「做不到」之前，先花十分钟跑一次**。这次实测的成本是一次脚本调用，
  省下的是外评一整轮。上面第 1、3 条错误若是直接发出去，等于浪费两次外评机会。
