# 双人协作规范 v2（学生A 搭骨架 / 学生B 后期润色）

> **这份文档管什么**：两个人怎么在同一个 GitHub 仓库里改东西而不互相踩脚、不改坏判定口径。
> **它不管什么**：任何判定口径、分数、权重、完成标准的具体数值——那些以 `docs/BACKLOG.md`、
> `docs/ROADMAP.md` 和项目计划书为准。想改口径，走"登记 → 核证 → 处置 → 落仓"，不在 PR 里顺手改。
>
> **三条底线**（谁都不例外）：
> 1. 匿名纪律：仓库内容与提交记录不出现真实姓名、学校名称；协作者一律用代号（学生A / 学生B / 评审）。
> 2. `docs/` 是唯一真相源；代码改了行为，文档必须同步，否则就是假声明。
> 3. `main` 只经 PR 进入，任何人（包括建仓库的人）都不直接 push、不 force push。

---

## 0. 开工前先确认的一件事（决定后面三件设置能不能用）

GitHub Free 的**分支保护**与 **CODEOWNERS** 对**公开仓库**可用；**私有仓库**要 Pro / Team 付费档。
所以先在仓库 Settings 里看一眼可见性：

- **公开仓库**：下面 1.1 / 1.2 / 1.3 全部照做。
- **私有仓库 + 免费账号**：分支保护用不了 ⇒ 退而求其次，靠"PR 流程 + 本清单"约束，
  并把仓库可见性改成公开后补上分支保护。**不要假设自己有分支保护却没设**——那是假安全感。

## 1. 一次性设置（建仓库的人做，做完不用再做）

### 1.1 邀请协作者

Settings → Collaborators → Add people，把学生B 的 GitHub 账号加进来，权限选 **Write**（可写）。

- 选 Write 不选 Admin：Admin 能改分支保护、能删仓库，学生B 不需要这些。
- 接受邀请后他才能 push 分支、开 PR。只发仓库链接是只读的，改不了东西。

### 1.2 保护 main（防冲突的核心机制）

Settings → Branches → Add branch ruleset（或 Add branch protection rule），目标分支填 `main`，勾这些：

| 设置项 | 勾不勾 | 为什么 |
|---|:---:|---|
| Require a pull request before merging | ✅ | 让 PR 成为唯一入口，杜绝直推 |
| Required approvals = 1 | ✅ | 至少一个人看过才能合 |
| Dismiss stale approvals when new commits are pushed | ✅ | 批完之后又改代码，批准自动作废，防止"批完偷换" |
| Require conversation resolution before merging | ✅ | 评论里的疑问必须逐条回复/resolve |
| Do not allow bypassing the above settings | ✅ | **关键**：建仓库的人默认能绕过保护，不勾这条 protection 对自己无效 |
| Allow force pushes | ❌ | force push 会改写历史、让别人的分支对不上 |
| Allow deletions | ❌ | 防止误删 main |

> 两条说明：
> - "Require status checks" 先**不勾**：仓库还没有 GitHub Actions CI，勾了会永远卡住不能合并。
>   等将来把 `verify.bat` 搬成 CI 再加。现在验证靠 PR 模板里的手动清单（见 §5）。
> - 如果网页上这些选项找不到，说明命中了 §0 的私有仓库限制。

### 1.3 让自己及时收到提交

两处都要开，缺一收不到：

1. **仓库 Watch**：仓库主页右上角 Watch → Custom → 勾 **Pull requests**（Pull request 打开、推送、合并都会通知）。
2. **个人通知设置**：右上角头像 → Notification settings → 确认 **Email** 和 **On GitHub** 都开着。
   - 只在 GitHub 站内看：通知在通知收件箱，默认只留 3 个月，标 Saved 才长期保留。
   - 要邮件：同一页勾 email；GitHub Mobile 还能开"Request to review a pull request"推送。
3. 学生B 开 PR 后，在 PR 右侧 **Reviewers** 里手动指定学生A —— 这会触发一次明确的 review 请求，比只看 Watch 更可靠。

### 1.4 CODEOWNERS：默认**不建**，原因是匿名纪律

CODEOWNERS 文件要把账号写成 `@用户名` 放进仓库，而分支保护的"Require review from Code Owners"也依赖它。
两人协作不需要自动化分派——PR 里手动指定 Reviewer 完全够，还能避免把账号名固化进仓库、碰匿名纪律。

**默认做法**：不建 CODEOWNERS，用 §1.3 的手动指定 Reviewer。
**只有当你确认"账号名进仓库不算违反匿名"、且想要自动分派时**，再建 `.github/CODEOWNERS`
（官方规则：文件放 `.github/`、仓库根或 `docs/`，路径区分大小写，最后一条匹配生效，账号必须有 Write 权限）。
这条不阻塞开工，先按默认走。

> 学生B 你好，仓库地址：`<仓库 URL>`。我已经把你加为 collaborator（Write 权限），请接受邮件邀请。

> **第一步先别改代码**，按顺序读这四个文件：

> 3. `docs/peer-brief-mvp-polish.md`（钦定方向：只做"把分数怎么来的讲清楚"，不要加功能）
> 4. `docs/COLLABORATION.md`（本文件：怎么分支、怎么交、验收清单）
>
> 读完先做两件事：① 在仓库里跑一次 `verify.bat /nopause`，确认是绿的；
> ② 回答 `docs/COLLABORATION.md` §3 里的 6 个设计问题（直接发我，或在 PR 里写）。
>
> **你要改的范围**：`docs/` 下我标注归你的文件（见 §4 表），以及新开的设计说明文档。
> **边界**：不改判定口径/分数/权重；不写真名和校名；不直接推 main；不 force push；
> 不确定的地方先问，不要猜着改。
>
> **怎么交**：从最新 main 开分支 → 小步提交 → 开 PR、填模板 → 在 Reviewers 里指定我 →
> 我按验收清单逐条检查后合并。细则都在 §5–§7。

**同时给他的四件套**（上面消息里已含，这里列全，缺一不可）：

| 给什么 | 具体内容 | 在哪 |
|---|---|---|
| 需求说明 | 钦定方向只有一个：讲清"分数怎么来的、凭什么可信"；不加新功能、不改判据 | `docs/peer-brief-mvp-polish.md` |
| 边界约束 | 匿名、docs 唯一真相源、不改判定口径、不推 main、写入范围 | 本文档 §3 §4 |
| 完成标准 | 每个 PR 必过的验收清单（可勾） | 本文档 §7 + `.github/pull_request_template.md` |
| 沟通方式 | 用 issue/PR 留言留痕；开 PR 指定 Reviewer；有疑问先问不改 | 本文档 §5 §6 |

**一个真实缺口**：项目计划书（含分工、里程碑、给学长的 6 个审阅问题）在**仓库外**，学长拉取仓库看不到。
我把这 6 个问题收进了本文档 §3，他读这一份就够；计划书本身要不要也放进仓库，你自己定。

## 4. 文件所有权（"我改的文件他不改"靠这张表落地）

口头说"你别改我的"没用，Git 不认识这句话。把范围写死在表里，PR 里对照检查。

| 目录 / 文件 | 主写 | 学生B | 说明 |
|---|:---:|:---:|---|
| `src/arena/**`、`tasks/**`、`tests/**`、`scripts/**` | 学生A | 只读 | 工程骨架与判定实现，学生B 发现问题开 issue，不直接改 |
| `fixtures/**` | 学生A | 只读 | 假提交夹具，改它等于改证据 |
| `docs/BACKLOG.md`、`ROADMAP.md`、`review-response-v1.md`、`diagnosis-report.schema.json` | 学生A | 只读 | 口径与决策真相源 |
| `docs/*peer-brief*.md`、`docs/*redteam*.md`、新建的设计说明文档 | 学生B | 可写 | 审阅意见、设计说明、叙事润色 |
| `docs/review-packet.md` | 学生A | 只读 | **生成物**，改它无效，要改先改 `review-packet-manual.md` 再重新生成 |
| `README.md`、`HANDOFF.md`、`docs/COLLABORATION.md` | 协商 | 可提 PR | 入口文档，谁改都要在 PR 里说明并同步另一处 |
| `verify.bat`、`push.bat`、`.github/**` | 学生A | 只读 | 基础设施 |

**交叉区怎么办**：学生B 想改学生A 的文件（或反过来）——不开 edit，开 **issue** 说明"想改什么、为什么"。
学生A 同意后，要么本人改，要么在 PR 里明确授权。这样两边永远不会在同一文件上同时动手。

## 5. 分支 / 提交 / 合并流程

### 5.1 分支

- `main`：受保护，只经 PR 进入。
- 学生A 的功能分支：`feat/<短名>`，如 `feat/b-26-review-page`。
- 学生B 的润色分支：`docs/<短名>` 或 `review/<短名>`，如 `docs/clarify-score-chain`。
- **一个分支一件事**，改完就合，别攒成一坨（攒大 PR 是冲突和返工的主要来源）。
- 开工前先同步：`git switch main && git pull`，再 `git switch -c <分支名>`。
- 分支落后 main 时，用 PR 页面上的 **Update branch** 按钮；**不要**自己 `rebase` 或 `force push`（会改写 SHA、让别人对不上）。

### 5.2 提交

- 格式：`类型(范围): 一句话说明`，如 `docs(review): 补分数链路说明`。类型用 `feat` / `fix` / `docs` / `test` / `chore`。
- 一次提交一个逻辑改动；"顺手"改的东西拆成另一个提交或另一个 PR。
- `commit` 前确认：没有真实姓名/校名、没有 `.env` 或密钥、没有本机绝对路径。
- push 前跑闸门：在按 README 建好的环境里运行 `scripts/push_gate.py`（Windows 直接跑 `verify.bat /nopause`，
  它的 [5b] 段会自动跑闸门），看到 `PUSH_GATE=CLEAN` 才推。
  空范围报 `NO_COMMITS` 是正常的（没有待推提交），不是错误。

### 5.3 PR 与合并

1. 学生B push 分支 → 开 PR，base 选 `main` → **按模板填完整**（`.github/pull_request_template.md`）。
2. 右侧 Reviewers 指定学生A；在正文写一句"请重点看 X"，省得对方逐行猜。
3. 学生A 收到通知 → 按 §7 验收清单逐条过 → 在 PR 里留言（通过了也留一句"清单全过"）。
4. 有疑问用 **Request changes**，写清"哪一行、为什么、怎么改才通过"；不要用模糊的"再想想"。
5. 全部通过后由学生A 点合并：
   - **默认 Squash and merge**（一个 PR 压成一个干净提交，main 线性好追溯）；
   - 只有 PR 内每个提交都值得单独保留时，才用 Rebase and merge。
6. 合并后删掉远程分支（GitHub 合并界面有勾选项），避免分支越积越多。

> 为什么强调 squash：仓库现在的 main 是线性的，评审包按提交追溯。merge commit 会插入额外的合并节点，
> 让"哪次改动对应哪件事"变难读。两人小步协作，squash 最省事。

## 6. 我怎么及时收到、收到后怎么处理

| 环节 | 做什么 | 判据（怎么算做到） |
|---|---|---|
| 收到 | §1.3 的 Watch + 通知 + 手动指定 Reviewer 三样都设 | 学生B 开一个测试 PR，你在站内**和**邮箱都收到通知 |
| 看到 | 收到后先约定一个响应节奏，比如"工作日 24 小时内给第一次回应" | 不是硬 SLA，是双方都清楚"多久没回算卡住" |
| 处理 | 按 §7 清单逐条勾；不通过的用 Request changes 写具体理由 | PR 里每条清单有结论（过 / 不过 + 原因） |
| 验证 | 自己拉分支跑一次 `verify.bat /nopause`，不只看对方说"我跑过了" | 输出 `RESULT: ALL GREEN`、`VERIFY_EXIT=0` |
| 争议 | 口径分歧不靠 PR 吵赢，登记到 BACKLOG，走"核证 → 处置 → 落仓" | 分歧有记录、有结论、有落点，不是口头过去 |
| 合并 | 通过后 squash 合并、删分支、必要时重生成评审包 | main 线性、评审包 `--check` 仍 OK |

**不要外发没验过的东西**：给外部评审/学长的报告，先跑 `verify.bat /nopause`（其 [4/5] 段会检查评审包），
或在按 README 建好的环境里运行 `src/arena/review_packet.py --check`，确认没过期。

## 7. 验收清单（PR 里逐条勾，任一条不过就不合并）

清单已固化进 PR 模板，开 PR 自动带出。

### A. 范围与口径（防跳步、防改坏判据）

- [ ] **一件事一个 PR**：能用一句话说清"这个 PR 改了什么"，说不清就是太大，拆开。
- [ ] **改动仅限 §4 归自己的文件**：越界改了对方文件 ⇒ 退回，开 issue 协商。
- [ ] **判定口径没被动过**：分数、权重、`gate_status` 三态、credit 分母一个没改；要改必须走登记流程。
- [ ] **没有"顺便"**：没有顺手重构、顺手优化、顺手修别的 bug；顺手的拆成独立 PR。
- [ ] **文档与代码同步**：行为变了，`docs/` 对应描述跟着变；找不到对应文档说明要先补文档。

### B. 可运行与可验证（不看自评，看命令输出）

- [ ] 一键验证实跑通过：`verify.bat /nopause` → `RESULT: ALL GREEN`、`VERIFY_EXIT=0`。
- [ ] 若是自己本地跑：贴出关键输出行，**不写"应该没问题"**。
- [ ] 新增/改了测试：贴出 pytest 结果（如 `48 passed`）。
- [ ] 若动了会影响用例数或评审包锚点的东西：评审包已重新生成，`--check` 输出 OK。
- [ ] push 闸门：`PUSH_GATE=CLEAN`（或明确无待推提交）。

### C. 可读与可维护

- [ ] 命名表达意图，不留下一个字母变量/`tmp`/`data2` 之类的临时名。
- [ ] 注释解释**为什么**，不解释代码在干什么；没有无主的 `TODO`。
- [ ] 关键逻辑有对应测试；测试名能看出"测的是哪种情况"。
- [ ] 没有硬编码的本机路径、密钥、账号（用环境变量）。
- [ ] 改动后 README / HANDOFF / 本协作文档的入口指针仍对得上。

### D. 匿名与安全

- [ ] 全文（含 commit message）无真实姓名、学校名称、昵称。
- [ ] 无 `.env`、密钥、token 进提交。
- [ ] 无 force push、无直接推 main 的痕迹。

## 8. AI 生成代码的质量要求（可直接并入 §7 验收）

学生A 本人也用 AI 写代码，这部分对两边都适用。判据写具体，不写"注意质量"这种空话。

### 8.1 可读、易维护

| 要求 | 怎么判（可判定） |
|---|---|
| 一个改动有单一职责 | 能用一句话说清；说不清就要拆 |
| 声明必须有执行者 | 文档/注释里每句"我们会……"都能指到具体代码或命令；指不到就是装饰，删掉或补上 |
| 有外部裁判 | 每条结论能对应 pytest / 变异测试 / 对拍 / 官方手册章节；给不出就标"假设"，不许说成结论 |
| 命名见意 | 变量名说明它是什么，函数名说明它做什么；不允许 `data2`、`tmp`、`flag` |
| 注释讲 why | 注释回答"为什么这么设计/为什么不那么做"；复述代码的注释删掉 |

### 8.2 避免"跳步式优化"（还没走稳就先跑）

判据（命中任一条即退回）：

- 一次改动同时做了"实现功能"和"优化性能/加抽象层"，**却拿不出**证明慢或重复的实测数据。
- 新增抽象层/配置项，但**只有一个调用点**或**没有任何调用方**——为"将来可能"提前铺路。
- 改了判定口径，但**没有**"登记 → 核证 → 处置 → 落仓"的记录。
- 在一个 PR 里同时改实现、改测试、改文档、改配置，**无法单独回滚其中一件**。
- 用"我先把框架搭大点，以后好用"解释——这正是仓库反复吃亏的模式（见 §8.4 的真实教训）。

正确顺序：**先跑通最小可用版本 → 实测暴露瓶颈 → 再针对瓶颈优化 → 每步验证。**

### 8.3 避免"过度防御性编程"（把不可能的情况都兜住，反而藏错误）

判据（命中任一条即退回）：

- 给"本不该发生"的情况加**默认值兜底**，把错误吞掉 —— 例：报告缺 `process_fact` 字段时默认 `false`。
  仓库的明确口径是**缺字段/非法值要报错**，默认会把"没记"当成"过程齐全"。
- `try/except` 大段包住核心逻辑，异常被吞掉后测试变绿 —— 这是假绿，不是通过。
- 为"不可能的输入"写分支，分支数比核心逻辑还多。
- 加 `if` 守卫只是为了让某个断言不炸，而不是表达真实业务规则 —— 守卫应该是规则，不是补丁。
- 用 `or {}`、`get(..., default)` 掩盖数据缺失，让报告"看起来完整"。

正确口径（本仓库已验证过的做法）：**缺字段报错、fail closed、无证据不记 0 分、作废整份排除**。

### 8.4 真实教训（都是踩过的坑，别重犯）

- 声明没有执行者：`derivation` 第一版的 `present/not_null` 是装饰，删掉后结果不变 ⇒ 改成缺字段拒跑。
- 自评式假绿：快照测试用同一对象引用，变异改了值两边一起变 ⇒ 改深拷贝后 7/7 DETECTED。
- 守卫被遮挡：整份排除挡在前面，导致另一条规则的变异 MISSED ⇒ 补独立样本恢复守卫。
- 环境写死：`verify.bat` 写死本机 Python 路径，换台机器全红 ⇒ 改成自动探测。
- 结论：**"看起来对"不算验证，能复现命令输出才算。**

---

## 9. 第一次协作的额外规则（新手容易忽略）

1. **不要 force push**。改错了就新提交纠正，或开新分支；force push 会让对方本地分支对不上。
2. **不要直接推 main**，哪怕只是改一个错别字——走 PR，哪怕 PR 只有一个字。
3. **不要提交 `.env`、密钥、token**；配置文件只提交 `.env.example`。
4. **不在私聊里改文件**：讨论留在 issue/PR 里，这样有据可查；"我刚帮你改了下"最难排查。
5. **不确定就问，别猜着改**。猜错的成本远高于问一句。
6. **小步、勤合**：每天能合一个小 PR，就好过攒一周的大 PR。
7. **匿名纪律优先于方便**：想写"某某大学""某老师"时，换成代号或删掉。
8. **生成物不手改**：评审包、schema 派生文件等先找生成入口，改源再重新生成。
9. **合并后同步**：合完 `git switch main && git pull` 再开下一个分支，避免基于旧代码开工。
10. **出了事先停**：发现红、发现冲突、发现口径对不上，先停下来说明，不要"试试这个试试那个"连续改。

---

## 10. 一句话总结

**分支保护堵住直推 → PR 是唯一入口 → 模板带出清单 → 清单靠命令输出判定 → 通过才 squash 合并。**

"我改的文件你不改"这句话，靠 §1.2 的机制和 §4 的表生效，不靠记性。
