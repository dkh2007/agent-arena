# agent-arena 架构说明（供外部评议，自包含版）

> 目的：让没有读过后端代码的人（或另一个 AI）也能判断这套架构哪里站得住、哪里是我拍的。
> 文中所有数字都可用文末命令在本仓库复核；标注「假设」的地方是**没有外部依据的判断**，不是结论。

---

## 一、它是什么

一个**编程训练器的判分与状态层**，外加一个 Android 原生前端。

用户拿到一个任务（例：给一段有 bug 的报表代码，要求修到通过断言），提交代码与运行轨迹；
系统按预设 rubric 判分，产出**可追溯的诊断报告**（错在哪个断言、属于哪类错误模式、下一步练什么），
再把这次结果沉淀成**技能掌握度**，据此推荐下一道题，最后要求用户用自己的话复述一遍解法。

产品形态：本地 Python 服务 + SQLite + Android 三页（报告 / 训练单 / 复述）。**不联网、不依赖云**。

规模（事实，可复核）：

| 项 | 数量 |
|---|---|
| Python 模块 | 32 个 `.py`（含 `__init__.py`），13949 行（`src/arena/*.py`） |
| 测试 | 1580 个用例，48 个测试文件，全绿 |
| 任务库 | 12 个 YAML 任务，分 4 族（debug / fix / prompt / retry） |
| 数据表 | 11 张（users / skills / tasks / error_patterns / submissions / user_skill_states / review_items / mastery_snapshots / arbitration_queue / reappraisals / unrecoverable_marks） |
| Android | 11 个 Kotlin 文件，3 页 + 共享组件 |

## 二、分层

```
L6 展示层     Android: 报告页 / 训练单页 / 复述页      + 本地草稿
L5 对外层     submission_api (HTTP) · review_packet (评审包) · test_evidence (测试证据)
L4 推荐层     training: 同族逐档推荐 + 四问提纲
L3 状态层     mastery (EMA+衰减) · scheduler (FSRS) · schedule_advisor
L2 判分层     trace_pipeline (现算) · assertion_evaluator · llm_judge (双判) · judge_pipeline (仲裁)
L1 报告层     diagnosis_report: gate → credit → 归因 → 错误模式
L0 定义层     tasks/*.yaml · vocabulary · taxonomy · report schema
```

数据流（一次提交的完整路径）：

```
提交(code + trace) → L0 取任务定义与 rubric
   → L2 按 rubric 逐项判：确定性断言（跑测试/查 JSON 字段）+ 语义项（双模型判，分歧进仲裁队列）
   → L1 组装报告：先算 gate（不通过则 credit 不给分）→ 归因到错误模式 → 绑技能
   → L3 把 error_patterns 折成该技能的掌握度证据（EMA + 时间衰减）→ 排下次复习时间
   → L4 按「同族下一档」推荐下一题，产出四问提纲
   → L6 渲染成三页；复述页把报告字段变成提纲问题，收文字/语音/手写三种输入，**不判分**
```

## 三、我刻意钉住的几条不变式（都有测试兜底，可证伪）

1. **不产半真报告**：判分前现算的每一项（如 R3 重试证据），与提交里自带的 raw 值比对，
   任一不符即抛 `PipelineError` 拒绝组装，不猜哪个对。
2. **每个字可追源**：报告与复述页上的每一句，必须来自任务 JSON 或词表；
   词表缺条目 → 抛 `FeynmanError`，宁可不显示也不编。
3. **跨文件对账**：`task_id` 是唯一对账键，报告 / 提纲 / 词表三处不一致即报错。
4. **判分分歧留档**：双模型判定不一致时进 `arbitration_queue`，人工改判进 `reappraisals`，
   不静默取平均。
5. **数字不许说过头**：评审包生成时会校验「文中写的用例数」与「现场收集到的用例数」，
   不一致直接拦下；测试证据档案必须带 commit + 环境 + 依赖 pin。
6. **不判分的部分明说**：费曼复述不自动判分，写进评审包并附可证伪点。

已实现并跑通：L0/L1/L2/L3/L5 + Android 三页；12 个任务里 `dbg-001` 用五份不同质量的假提交跑出 0 / 0.25 / 0 / 0 / 1.00 的区分度。

## 五、我自己拿不准的五个点（想请外部评审的正是这里）

1. **判分误差会污染长期状态。** L3 的掌握度吃 L2 产出的 `error_patterns`。若 L2 把「写对了」判成「写错了」，
   这个误差会顺着 EMA 沉进掌握度，并影响后续推荐。现在只有 `reappraisals` 做**人工**事后改判，
   **没有自动降权或回滚机制**。→ 该不该引入「证据冲突时降权 / 可回滚重放」？
2. **掌握度超参是拍的。** EMA 的 λ 与时间衰减半衰期都写死在代码里，**没有用数据校准过**，也没有做敏感性分析。
   → 可识别性怎么办？换轻量 BKT 是否更站得住？
3. **推荐无探索。** 「同族逐档」是纯规则：同族内按难度升一档。用户在某档卡住就一直卡。
   → 是否该加一个极简 bandit（ε-greedy）做探索？代价是推荐理由变难解释。
4. **复述不判分，产品上是把「对不对」的判断交回给用户。** 教学上这站得住（费曼技巧的前提是自己发现缺口），
   但用户可能不知道自己对不对。→ 是否该做「给参考答案后自评对照」这一步？会不会破坏费曼的原意？
5. **信息架构没有对标。** 三页（先报告、再训练单、最后复述）的顺序是我按数据结构倒推的，
   没有和任何同类产品做过逐项比对；也没做过真人可用性测试。
   → 这个顺序在「演示给别人看」和「自己天天用」两个口径下是否都成立？

另外一个元问题：**单人项目、32 个模块、13949 行、11 张表**，是为了「可追溯」付出的复杂度。
→ 这是否已经过度工程？如果要砍，先砍哪一层？

补充一条已经拍过的口径，供评审判断一致性：**「整份不合格」的提交仍然提供技能证据**
（理由是「数据缺失 ≠ 能力不足」），所以成绩单上分数列与掌握度列分开写、不同行出现。
这条口径与上面第 1 点直接相关——如果不合格报告也能抬掌握度，判分误差的影响会被放大还是被稀释？
