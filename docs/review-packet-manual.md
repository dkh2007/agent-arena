## 1. 项目一句话

Agent 开发学习领域的**自适应诊断与训练闭环**：学习者提交一个 Agent，平台对其**执行轨迹**做错误诊断
（不只打分），把错误模式映射到技能缺口，按遗忘规律调度**可执行的任务变体**作为复习项，
并按「掌握度 + 遗忘风险 + 错误热度 + 项目截止」生成训练建议排期。

一句话区分：**现有平台（PinchBench / ClawBench / 千问 Arena）评模型；我们评学习者的技能缺口。**

## 3. 已定决策（不再重议，新提议请走"登记→核证→处置→落仓"流程）

1. **首发域 = Agent 开发学习**（算法题域推迟到决赛，不做）。
2. **评测层 = 自研断言层 + 可选旁证画像层**。A2E 已实测证伪：26 个指标全是聚合分或 LLM judge，无任务级布尔断言；
   `self_correction_rate` 对真假重试同判 1.0。**证据在 `spike/README.md`（三级：代码 / 运行 / 语义），本文不复制**——
   若你需要核验，请索取该文件或让作者贴出对应测试。
3. **复习项 = 可执行任务**（变体 / 故障注入调试题 / 限时练习 / 错题重放），不是抽认卡；FSRS 只回答"何时复习哪项技能"。
4. **评分两段式 gate / credit**（P6 拍板）：`gate` = 交产物 + 正常退出，不计权重、fail 即 0 分；
   `credit` = 结果正确 2 + 过程证据 1 + 无参数幻觉 1，**分母恒为 4**。
5. **门禁只管分数，不管观测**：门禁失败时 credit 层照常判定并记录，另存 `counterfactual_credit`（反事实得分）
   表示"若算分能拿多少"，仅供诊断。**唯一分数是 `ratio`**，该字段不得被任何汇总当分数读（Q1 处置，round-70）。
6. **P5 拍板：不新增第 4 技能**，"没交产物"走 gate 通道，用 `disqualifying_assertions` + `unattributed_patterns` 两个字段留痕。
7. **数据缺失 ≠ 能力不足**：`blocked` / `unscored` 一律不计入掌握度、不产出错误模式（这是 A2E"漏报拿满分"的反面）。
8. **P1 拍板：掌握度与调度分开记，且只用一个时间轴**。「会不会」由最近做题表现估计并随时间衰减；
   「什么时候再练」由间隔重复卡片（FSRS）的参数决定。**不把 FSRS 的 stability 当作掌握度的衰减系数**——
   S 的定义是「可提取性降到 90% 所需天数」（值域可达上万天），与平滑系数的值域 (0,1) 不可直接换算，
   两者只能经一个**待标定的映射**关联（登记为假设，须留出数据消融）。原「掌握度 = FSRS 的 R 值」写法作废。
9. **P2 / Q5-D1 拍板：按题目类型决定「缺过程」怎么算**。任务 YAML 的 `submission_requirements.requires_process`
   声明本题要不要过程。要过程的题缺过程 ⇒ **本次不计能力分、不计掌握度、不产错误模式**，记一条中性流程事实
   （`process_fact`）并提示补交；只交答案的题照常算分。**「缺过程」是流程事实，不是能力判断**；
   写了「没思路」也算交了过程，不把「没写」当「不会」。
10. **P3 拍板：防作弊保「答案可对账」，随机化只作补充**。答案里的数值必须能由过程记录里的工具返回值推导；
    对账不通过 ≠ 答错，落「未验证」（不计掌握度、不记短板）。**前提代价**：过程记录必须含被用到的数值，
    否则无据可对——这是补齐记录字段的理由，不是放弃对账的理由。
11. **TD-038 拍板：任务版本不一致 ⇒ 本份作废（`voided`）**。报告照出、断言判定照给、分数不算、不计掌握度，
    `void_reason=task_version_mismatch`，并提示「请按当前版本重交」。**拒绝出报告 = 沉默丢单，判不合格 = 冤案**，
    两者都不取：作废用的是「这次不算数，但不是你不会」这一档。

## 7. 每条决策怎么当场验（不需要读代码）

第 3 节那 11 条，不必只靠"信"。每条都配了一个现场动作：

```bash
python scripts/demo_decision.py           # 总表：11 条按可演示性分三档
python scripts/demo_decision.py 4         # 只看第 4 条
python scripts/demo_decision.py --all     # 全跑；退出码 0 = 无 FAIL
```

输出分四档，**其中两档不算通过**：

| 档 | 含义 |
|---|---|
| `PASS` | 该决策中"可在本机判定"的主张，实测全部成立 |
| `PARTIAL` | 只有一部分主张可在本机判定，其余依赖外部材料或尚未实现的模块 |
| `NOT_EXECUTABLE` | 仓库里没有可执行载体（阶段未到，不是失败） |
| `FAIL` | 可判定部分有任一不成立 |

当前结果：**PASS 7 / PARTIAL 3 / NOT_EXECUTABLE 1 / FAIL 0**。三条 `PARTIAL`（决策 1 / 2 / 8）
与一条 `NOT_EXECUTABLE`（决策 3）的剩余部分**不由脚本担保**——这正是把它们单列、不并入 PASS 的原因。

两条写进脚本的自我约束，供你核对：

1. **标题从本文件现读**，脚本不复制决策正文（否则就是第二个真相源，改一处漏一处）；
2. **期望值从任务 YAML 现读**（例如"分母恒为 4"的那个 4 取自 `scoring.score.credit.total_weight`），
   读不到直接报错，不许默认 0 让判据静默变红。

**这个脚本自己会不会永远绿？** 有 5 条变异测试专门破坏实现——把反事实得分抹成 0、让"缺过程"永不成立、
让作废恒为 false、让 `unscored` 计入掌握度、给门禁条目加权重——要求对应演示**必须变红**：

