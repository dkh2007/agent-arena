# 跑批手册（B-04h ③）

> 适用范围：判据（`tasks/*.yaml` 里的 `rubric_gate` / `rubric_credit`）改动之后，
> 把历史作答按新判据重算一遍，并把"谁的分数变了、要向谁说什么"交代清楚。
> 代码入口只有一个：`src/arena/cycle.py`。本文件回答**人**的那一半：
> 什么时候跑、谁跑、谁发、出问题找谁。

## 0. 三个角色（名字待填，现在不编）

| 角色 | 做什么 | 谁 |
|---|---|---|
| 执行人 | 跑命令、看清单、把结果贴给复核人 | `<执行人>`（默认本项目维护者，人工发起） |
| 复核人 | 看"分数变化清单"，确认后在命令里署名 | `<课程负责人>` |
| 发布人 | 在后台把页面上那行字发出去，回填发送时间与人数 | `<助教>` |

三个人可以是同一个人（演示阶段通常是），但**署名那一步不能省**：
`--approved-by` 会写进每条重评记录的理由里，事后查"这批为什么被改"时它是唯一线索。
代码里没有"自动发通知"，也没有定时任务——这两个决定都是刻意的，理由见 §5。

## 1. 什么时候跑

**只有一件事触发：判据变了。** 判据变没变不由人记，由指纹判：

```bash
cd agent-arena        # 仓库根；本机的完整路径按你的环境替换，不写进仓库
PYTHONPATH=src python -c "from arena import diagnosis_report as d; \
  t = d.load_task('tasks/dbg-001-order-report.yaml'); print(d.rubric_fingerprint(t))"
```

- 与上次记录的值**不同** ⇒ 必须跑一次（改期望值、改措辞、改权重、增删规则、调顺序，全在这一个指纹里）；
- **相同** ⇒ 不用跑。改标题、改描述这类不影响判分的字段不会动指纹，也就不必跑。

另外两个固定的跑点：

1. **学期末出正式档案之前**：跑一次演练（不署名），确认"没有人的分数停在不该停的标准上"；
2. **补了历史产物之后**（如果将来做了平台侧抓包）：先撤销对应的终止标记，再跑一次。

## 2. 五步

### 第 1 步 演练（不写库）

```bash
cd agent-arena
PYTHONPATH=src python -m arena.cycle --db "<库路径>" \
  --task tasks/dbg-001-order-report.yaml \
  --reason "R2 期望总额修正（原值写错 1 元）" \
  --changed-on 2026-11-10 \
  --what-changed "改了「报告总额」这条判据的期望值：原值少算了一元" \
  --archive "workbench/cycles/2026-11-17-r2"
```

演练**一个字都不写**：不追加重评、不动分数、不刷掌握度。它给一张清单：

- `score_changed`：分数会变的份数；
- `needs_review`：差值超过复核阈值的份数（这些必须逐份看，不看就不许发）；
- `pending_mastery`：0 分但过程证据进过 P 的那批（口径未定，落在"待定"格）；
- `retired`：已标「确认不可回溯」的份数（本次不重试，但文案照发）。

### 第 2 步 复核人看清单，然后署名

看的是 `--archive` 目录里的 `cycle.md`：数 + **每条要发出去的原文**。
演练给的文案与真跑发出去的**逐字相同**（同一组模板），所以现在看到的就是学生将来看到的。

确认无误后，同一条命令加 `--approved-by "<复核人>"`（换一个新归档目录，不许覆盖上一次）：

```bash
cd agent-arena
PYTHONPATH=src python -m arena.cycle --db "<库路径>" \
  --task tasks/dbg-001-order-report.yaml \
  --reason "R2 期望总额修正（原值写错 1 元）" \
  --changed-on 2026-11-10 \
  --what-changed "改了「报告总额」这条判据的期望值：原值少算了一元" \
  --approved-by "<复核人>" \
  --archive "workbench/cycles/2026-11-17-r2-applied"
```

执行阶段会**先自己再演练一遍**，再写库，然后把两次结果逐份对比（份数、id、每份差值）。
对不上就停下并报"演练与执行不一致"——那说明两次之间库被改过（并发或手工），
此时继续写等于拿一份过期清单当依据。

### 第 3 步 发布人发那行字

`cycle.md` 的「要发出去的那几句」就是全部内容，**工具不发送**。
发布人做的事：

1. 在后台按 `submission_id` / `user_id` 找到记录，把对应文案贴到与分数同屏的位置；
2. 在 `cycle.md` 的 checklist 上勾掉，写下发送时间与人数；
3. 有学生来问时，只用这条记录里的原文回答，**不额外解释**——加一句自己的理解，
   就会变成第二套口径。

### 第 4 步 归档

每次跑批一个目录：`workbench/cycles/<日期>-<一句话>`，里面 `cycle.json` + `cycle.md`。
目录不覆盖（覆盖等于抹掉上一次的证据），所以执行阶段用另一个目录名。

### 第 5 步 补标记（只对真的回不来的）

`retired` 那一格不是自动的，需要人一条条确认。确认后用代码打标记（带理由、带人名）：

```python
import sys; sys.path.insert(0, "src")
from arena import store
conn = store.connect("<库路径>")
store.mark_unrecoverable(conn, "<submission_id>",
                         reason="v4 之前提交，产物未随 trace 落盘，旧备份里也没有",
                         marked_by="<复核人>")
```

打错了就撤销（不删行，保留"谁在什么时候说过它补不回来"）：

```python
store.revoke_unrecoverable(conn, "<submission_id>", reason="产物其实还在另一个备份里")
```

## 3. 出问题怎么办

| 症状 | 说明 | 处置 |
|---|---|---|
| `演练与执行不一致` | 两次之间库被改过 | 停下，查并发/手工改动；重跑演练再批，不要跳过去 |
| `needs_review > 0` | 差值超过阈值 | 逐份看原始报告，确认是判据该改的结果再发 |
| `retired` 突然变大 | 有人批量打了终止标记 | 先看标记表的 `marked_by` 与理由，再决定是否撤销 |
| 学生说"我的分被改了" | 可能是本次跑批，也可能是更早 | 用 `notices` 里那条记录对，不对上就查重评链，不许口头解释 |
| 报告越跑越长 | 补不上的行还在被反复重试 | 那是刻意的；要停就按 §2 第 5 步逐条确认后打标记 |

## 4. 判据（做到什么算做完了）

- 演练跑过，且 `cycle.md` 里每一条 `recalculated` / `legacy_scored` 都有四件（变了什么、
  为什么是我、能和什么比、下一步做什么）；
- 执行有署名，重评理由里能看到"经谁确认"；
- 待发清单的条数 = 发布人实际发出去的条数（两个数对得上才许说"通知完了"）；
- 归档目录里能独立看懂这次为什么跑、跑了什么、还差谁做什么。

## 5. 刻意不做的三件

1. **不自动发通知**：发出去收不回来；代码只产出清单。
2. **不定时跑**：判据改动是人的动作，跑批也该由人发起。加一个 cron 只会让"为什么昨天分变了"多一种无法追责的来源。
3. **没有署名不写库**：写库会追加重评、刷新掌握度，这两样都改学生看到的东西。
   一次没有署名的批量改分，事后无从追责。
